# rsi-ladder — 递归阶梯：RSI 的"递归"到底在哪

配套 skills/evo/SKILL.md「递归阶梯」一节。**递归 = 改进对象逐层上移**——每一层的
改进对象都是上一层「跑出来的产物」之一。普通使用到 L1 就够；往上走每层都要更严的门禁。

## 阶梯总表

| 层 | 改进对象 | 谁批准 | 门禁要点 |
|---|---|---|---|
| L1 | 产物（baseline 内的文档/代码/skill/提示词…） | 冠军地板 + 回归 | 无需人类点头即可圈内自动推进，但要汇报 |
| L2 | 标准（evals/criteria.md、regression.md） | **人类签收** | 防 agent 改标准作弊；谁改谁签 |
| L3 | 协议（本手册、evo-round 脚本、工作区布局） | 冻结基准 A/B + 双人评审 | 协议是"机器的基因"，改动要有对照实验 |
| L4 | agent 自己的能力（工具/技能/记忆管线） | 默认关，平台可逆才开 | 可逆、可查、重启可恢复 |

## L1 — 进化产物（人人都该用的那层）

日常形态。你在元层和用户对标准 → 跑圈 → critic 打分 → 冠军地板吸取。门禁就是
防退化三件套。**这一层可以做到完全不碰 L2**，用户甚至不必知道标准也能进化
（默认标准：`evals/criteria.md` 里的 placeholder + 用户随口说的方向）。

## L2 — 进化标准（偶尔，必须有人的那层）

标准本身也是产物，可以被进化，但**只有人类能签收**（agent 擅自改标准 = 作弊窗口：
"把门槛改低然后宣布赢了"）。触发场景：
- 用户看了几圈结果说「其实我更在意 X」→ 把 X 写进 criteria（规则 1 形态）；
- critic 分歧升级时用户裁定 → 裁定结论落成新标准（critic-and-fuzzy 规则 3）。

操作：元层起草 diff → 用户过目 → 用户确认后合入 evals/。改标准本身也记账
（ledger 加一行 `criteria change rN: +<新标准>（用户签收）`）。

## L3 — 进化协议（工程行为，双人评审）

协议 = 本手册 + 引擎脚本 + 工作区布局。改动协议 = 改变"机器怎么进化"的基因：
- 门禁：先在**冻结基准**上 A/B——同一条基线+同一组标准，新旧协议各跑 N 圈，
  比较（入选率、平均分增量、成本、回归率）；另一名评审人复核设计；
- 改动入 ledger（`protocol change rN: ...`）+ git tag；
- 回滚入口永远保留（旧协议 = 上个 tag 的脚本）。

为什么这么严：协议 bug 会在每一圈**复利放大**——一个坏的相似度偏好会让几十圈
全往一个错误方向跑。

## L4 — 进化能力（默认关，平台可逆才开）

改进对象 = agent 自己的工具/技能。这是研究圈 RSI 最常指的那层，也是风险最高的一层：
- 默认关闭。只有平台支持「热挂载 + 可逆卸载 + 重启恢复」才允许试点——dsh 的
  cordis 热重载 / devserver 热替换满足；裸 CLI 环境不满足就保持关。
- 试点形态（rather than 直接改核心）：给会话加一个临时工具/技能 → 用几圈
  验证它确实提升指标 → 用户在设置里确认保留。dsh 生态已有参照实现：
  `dsh-evolve`（会话内 evolve_add/evolve_remove 热挂载插件）、
  `dsh-memory-evolve`（经验蒸馏 → 技能自动创建）。
- 门禁：可逆（一键回滚）、可查（改动可见）、人工默认在场、预算更紧。

## 禁止自动进化的东西

- **核心系统代码/安全边界**：任何让进化改到"自己判断能力之外"的机制（权限提升、
  eval 注入、改 prompt 沙箱）一律禁止，即使用户在场也要单项明确批准。
- **用户资产外部**：进化只作用于用户指认的 workspace 内的产物，不扫描不触碰
  workspace 外的文件。
- **标准本身绕过门禁**（见 L2/L3）：任何"顺手把标准改宽松"的行为都算作弊信号。

## 一个判断问题

每当你（agent）想动"改标准 / 改协议 / 改我自己的配置"，先停一下：
**这是 L2/L3/L4 动作，需要人类签收或平台能力支撑吗？** 是 → 停下，走门禁。
